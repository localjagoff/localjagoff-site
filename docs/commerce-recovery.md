# Checkout And Draft Fulfillment

## Contract

Printful remains the retail-price/variant source. `commerce-policy.cjs` shares the existing store, hidden product and name rules with the storefront API. There is no second price database. Checkout ignores cart prices, names and images in favor of the server product lookup. Frontend pages and displayed price calculations are unchanged.

Only a product returned by the configured store, with a matching synchronized, non-ignored variant and explicit `active` availability, can enter a new Checkout Session. Unknown availability fails closed. This is sync-variant availability, not a reservation of regional stock. Quantities must be positive integers, maximum 99 per line. A cart exceeding Stripe's 500-character metadata value limit is rejected before session creation; the new compact metadata format holds more lines than the old format. Client-supplied return origins are ignored; `SITE_URL` is server configuration, defaulting to the existing production domain. Shipping remains US-only, USD, $5.99; promotion codes remain enabled.

The fulfillment policy is unchanged:

Paid Stripe Checkout -> Printful DRAFT -> owner reviews -> owner manually confirms/pays -> Printful fulfillment.

Never call an order-confirmation endpoint or change `confirm=false`. Both the query parameter and draft request body explicitly disable automatic confirmation. Existing pending, fulfilled or canceled orders are never overwritten or recreated by a retry.

## Verification And Persistence

The route verifies the unparsed request body with Stripe's webhook signature and endpoint secret. It handles `checkout.session.completed` and `checkout.session.async_payment_succeeded`, retrieving the current session from Stripe before checking payment, currency, store and environment. Unpaid sessions do not create orders. Test-mode Stripe events are acknowledged but do not contact Printful or email customers. Live credentials are rejected in Vercel preview/development checkout and fulfillment paths. No live Printful sandbox orders are generated by the test suite.

Version 2 metadata retains product ID, sync variant ID, quantity and the server-resolved unit price at session creation. Fulfillment compares quantities/unit amounts with Stripe line items and validates subtotal/total math. It supplies customer retail prices, discount, shipping and tax to Printful separately from Printful's manufacturing/shipping costs. It never sets Printful's own cost price. Shipping uses Stripe's collected shipping address, not an implicit billing-address fallback.

Old sessions without a metadata version must reconcile their line prices against current Printful retail prices before any new draft is created. A legitimately changed retail price, unavailable legacy item, missing shipping address or underpriced old session requires owner review; do not bypass the check to clear retries.

An order's external ID retains the existing `LJ` plus first 24 SHA-256 hex characters of the Checkout Session ID. Printful enforces store-unique external IDs. The worker looks up `/orders/@{external_id}` before creation and again after an uncertain/failed create. Non-404 lookup failures never trigger a blind POST. Concurrent requests may attempt more than one POST, but converge on the single uniquely keyed order. A known linked order disappearing requires manual recovery, not automatic recreation.

Stripe Session metadata records `printful_external_id`, `printful_order_id`, last-observed `printful_status`, `fulfillment_state`, `fulfillment_event_id` and a sanitized `fulfillment_error`. These are operational correlation fields, not another product database or a real-time Printful status feed. Failures return HTTP 500 for Stripe delivery retry. Logs contain IDs and error categories, not shipping/customer payloads. If Stripe metadata persistence also fails, the structured log and deterministic external ID remain recovery evidence.

Order email is best-effort and does not reverse a paid draft. A Resend idempotency key and Stripe `order_email_sent` marker reduce repeat sends. Resend's key expires after 24 hours; a send succeeding while persistence fails can still cause a duplicate email on a much later replay. Email errors require operational attention; there is no email retry scheduler.

## Recovery

1. Inspect the failed Stripe event, Checkout Session and `fulfillment_state`; confirm payment and the correct environment/store. Do not ask the customer to pay again merely because draft creation failed.
2. Find the linked Printful order by `printful_order_id` or the deterministic external ID. Do not delete that ID, clone an existing order, or create a second manual order to bypass an uncertain response.
3. Correct the underlying credential, address, product/variant or API outage issue. Compare old-session prices with payment records and the price history before any owner-approved manual resolution. Do not change the customer's paid amount automatically.
4. Resend the original event from Stripe after correction. The existing external ID will be reused. Stripe retries are finite; monitor failed events and reconcile paid sessions with linked drafts after that window. No queue, alert service or scheduled reconciliation job was added.
5. Only the owner reviews and confirms/pays the draft in Printful. Shipping notices and actual fulfillment still depend on Printful/owner settings and must be checked separately.

## Test And Rollout

Use Node 24 for the local Node test runner (the repository already mixes ESM and CommonJS API files).

```sh
npm install --ignore-scripts --package-lock=false
npm test
npm run build
```

Tests use synthetic fixtures and mocked Stripe/Printful providers, plus the real Stripe SDK to check raw-body signatures. They do not create real Stripe Sessions, charges, Printful drafts, fulfillment requests or emails. `next build` verifies the Pages Router application, not deployment of the separate root `api/` Vercel functions; route and helper tests supplement it. The existing mixed module style can emit a Node module-type warning.

Before production rollout, verify the deployed runtime, API function packaging, raw webhook body handling, provider permissions and mode separation in an isolated environment. Review actual sync-variant availability fields against the store. Keep `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `PRINTFUL_API_KEY` and optional `RESEND_API_KEY` server-only; never put them in `NEXT_PUBLIC_*` variables. Set a preview-specific `SITE_URL` and only test Stripe credentials in preview. Stripe test events intentionally stop before Printful; a full provider contract test would need separate, explicitly approved test infrastructure. Do not use production purchases as testing.

Deploy checkout and webhook changes together; the old webhook cannot interpret version 2 metadata. After new sessions exist, do not roll back only the webhook to the old parser. A safe rollback must retain version 2 parsing and server-side pricing or pause new checkout while reconciling outstanding sessions.

The hardcoded public `/api/get-order` diagnostic is retired with a no-store 404 response. It is not an authenticated customer order-status page. No storefront callers were found.
